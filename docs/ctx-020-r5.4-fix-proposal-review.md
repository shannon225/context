# CTX-020 r5.4 fix proposal: request for independent review

- **Prepared:** 2026-11-19.
- **Branch:** `ctx020`.
- **Base for line numbers:** commit `1cf1985` (r5.3 implementation). Later commits on the branch are documentation only.
- **Status:** a **proposal**. No code has changed, and Ariana hasn't approved it.

Please review the reasoning and the proposed changes, say whether you agree, and report anything missed. **Do not edit code.**

## 1. Background you need

**What CTX-020 does (r5.3)**
- Context scores targeted PRM/DIA assays.
- A discriminant (Percolator) is trained on the **background** peptide population and applied unchanged to the **reference** (assay) peptides.
- CTX-020 makes every assay peptide get scored:
  - it searches the full gradient;
  - any assay peptide or matched search decoy without a valid pre-competition score is **force-scored** through the existing candidate and target-decoy (TDC) path;
  - when nothing passes the usual fragment-correlation gate, a **weak fallback** keeps the best-scoring peak.
- Authority: `docs/uu-ctx-020-forced-assay-xic.md`, section "Current decision and handoff" (r5.3).

**What prompted this proposal**
- Round-2 assessment over 9 seeds (`docs/validation/ctx020-confidence-assessment-2026-11-18.md`), Context + Percolator, compared with pre-CTX-020 plus the CTX020-035 range fix.
- **Calibration** looks unchanged.
- **Coverage and ranking** are slightly better: AUPRC +0.015.
- **Confident identifications are lower:** a median of **6 fewer targets at PEP < 0.01, lower in 8 of 9 seeds**.
- The round-2 code review (`docs/ctx-020-review-2026-11-18.md`) raised two candidate causes, findings 2 and 4. Ariana asked for a fix round on both.

## 2. Finding 2: proposed to drop (please confirm)

**The claim.** The weak fallback (`src/main/java/org/searlelab/context/encyclopedia/EncyclopediaTwoPointOneScoringTask.java`, lines ~425–427) adds the candidate with `bestScore`, captured *before* the LDA rescoring that normal candidates get (lines ~401–414). Forced weak candidates would then compete in `trim(1)` on a different score scale.

**Why I think it has no effect in Context**
- The rescoring runs only if `((EncyclopediaTwoLDAScorer) scorer).getLDAScorer()` is present.
- That scorer is built in `EncyclopediaTwo.java` (line ~414) from the `prelimAnalysis` argument.
- Context's only production call passes `Optional.empty()`: `ContextFeatureScorer.java` lines ~289–290, `EncyclopediaTwo.generateFeatureFile(..., java.util.Optional.empty(), java.util.OptionalInt.empty(), pairs::record)`.
- So the "LDA score" is just `score`, and `auxScoreArray[0]` is already `score` (line ~362).
- The fallback and normal candidates are therefore on the same scale.
- Only EncyclopeDIA's own two-pass search (`EncyclopediaTwo.java` lines ~321–338) supplies a preliminary LDA, and Context doesn't call it.

**Please check**
- Is there any other Context path, current or likely soon, that passes a non-empty `prelimAnalysis` into this scoring task?
- Is it worth a small defensive change (route the fallback through the same rescoring helper), or should it be left alone?

## 3. Finding 4: the proposed fix

Background features come from the original EncyclopeDIA path. Assay peptides (all assay rows and their matched search decoys) take a modified path. The background-trained model is then applied to features that, for assay peptides only, are computed differently.

| # | Current assay-only behavior | Background behavior | Proposed change | Location (at `1cf1985`) |
| --- | --- | --- | --- | --- |
| a | **Scan set.** For each assay row, request all fragment scans over the whole run whose isolation range contains the precursor m/z, sort them by time, and reload every MS1 scan. When isolation windows overlap, scans from several windows are interleaved, roughly doubling scan density. The E-value null is then built from this merged set. | Scored against the stripes of the single isolation range being processed. | Use the same range's stripes and precursors that background uses: the `stripes`/`precursors` passed to `getScoringTask`; in `completeAssays`, that range's `getStripes`/`getPrecursors`. | `encyclopedia/ContextEncyclopediaScoringFactory.java` lines ~64–67 (and ~133 in `completeAssays`) |
| b | Local window length `upperWindow - lowerWindow + 1`. | `upperWindow - lowerWindow` (original EncyclopeDIA; drops the last scan). | Remove `+1`. | `EncyclopediaTwoPointOneScoringTask.java` line ~249 |
| c | Keeps fragment chromatograms whose total intensity is 0. | Drops them before smoothing and refinement. | Remove the assay exception. | same file, line ~263 |
| d | Checks that the isotope packet is long enough before reading the monoisotopic and +1 peaks. | Reads them directly. | Keep only if it is needed to avoid an exception; document it if kept. | same file, lines ~310–312 |
| e | Second `scoreChromatograms` pass over "scans inside the window". Under r5.3 the window is the whole run, so the result is the same. | No second pass. | Skip it when the window covers the run. | same file, lines ~201–209 |

**Unchanged:** the weak fallback, finite-value checks, detection tracking and statuses, report format, IDs, schema, and background behavior. Whether to bump the run-level cache identity version (`assay-full-gradient-scoring-v2`) so r5.3 outputs aren't reused is decided during implementation.

**Please check**
1. Do you agree that (a)–(c) make assay features differ from background features? Which do you expect to matter most?
2. **(a)** Is using the single processing range correct when a precursor m/z lies in two overlapping isolation windows?
   - Background would score the entry in whichever range(s) the library assigns it to.
   - Could this lose assay coverage, for example a precursor only in a range that is skipped as sparse?
   - Should the forced pass in `completeAssays` pick the range the same way background does?
3. **(b)** The `+1` may have been added so a short assay window never yields zero scans. Under full-gradient scope, is there any remaining case that needs it?
4. **(c)** Keeping zero-sum fragments may have been added so a peptide with no fragment signal still produces a finite feature row and counts as DETECTED. Would removing it make such rows unscorable, throwing or changing their status? If so, what should happen to them under r5.3's DETECTED definition?
5. **(d)** Does `PrecursorScanMap.getIsotopePacket` always return a full-length packet?
6. **Population consistency.** Is anything else in the assay path (`xic/AssayScoringTask`, the factory, `EncyclopediaTwo` assay branches) still asymmetric with background in a way that would shift feature distributions?
7. Is there a more plausible cause for the PEP<0.01 loss that this proposal ignores? Two candidates:
   - the reference population roughly doubled (about 320 against 190 peptides per seed), mostly forced low-quality candidates, which changes the reference decoy distribution that pyIsoPEP fits;
   - review finding 3 (asymmetric forcing).

## 4. How the fix would be judged (CTX020-045; criteria fixed in advance)

- **Noise floor:** rerun Context-Percolator on the existing r5.3 features with background training seeds 1–5, plus one same-seed rerun to confirm determinism.
- **Comparators:** the 9-seed matrix, compared with r5.3 and with pre-CTX-020 plus the range fix, using `docs/validation/ctx020_confidence_assessment.R`.
- **Calibration is worse if any of:**
  - pooled upper-bound entrapment FDP at PEP<0.01 is above both 1% and r5.3 (1.0%) by more than the noise floor;
  - the count-weighted mean |lower FDP − mean PEP| across bins rises beyond the noise floor;
  - more bins have a 95% CI entirely above the diagonal (r5.3 seed 1 has 4 across all ten bins; reference count corrected with Ariana's approval on 2026-11-19);
  - pooled q≤0.01 entrapment FDP rises beyond the noise floor (reported with and without seed 2).
- **Sensitivity is worse if any of:**
  - the median paired change in PEP<0.01 targets is negative beyond the noise floor, or the fix is lower in ≥7/9 seeds;
  - median AUPRC falls beyond the noise floor;
  - maximum recall drops.
- **Hard gates:** 9/9 runs complete; 576-row detection reports; feature/pair ID parity; no assay identity in background; background-only output byte-identical.
- **Limits:** n=9 and about 5 entrapments at PEP<0.01. This catches clear regressions but cannot prove equivalence. Entrapment FDP is probably inflated by off-schedule genuine signal, equally across builds.

**Please check:** are these criteria sensible? Is anything missing, for example a per-feature distribution comparison between assay and background rows before and after the fix?
