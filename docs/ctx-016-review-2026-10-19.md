## Findings

### 1. P1 — scoring-worker failure does not fail feature generation

Location: `src/main/java/org/searlelab/context/encyclopedia/EncyclopediaTwo.java`, line 522 (discarded Future), lines 530–537 (termination-only wait), and normal return after consumer cleanup.

`executor.submit(...)` captures worker exceptions in Futures, but the search discards those Futures and never calls get. The pinned upstream `ThreadableTask.call` logs and rethrows failures; that does not propagate them to the caller waiting only for executor termination. A run can therefore lose scoring tasks and still return its partial feature output normally. Missing candidates can change both identification counts and target/decoy score populations. Existing sidecar validation checks rows that were emitted; it is not a completeness check against every submitted task.

Reproduction uses [ContextScoringFailureProbe.java](validation/ContextScoringFailureProbe.java), the small repository library/acquisition/FASTA fixture and the unchanged feature-only search. It bypasses prediction and deliberately fails the first scoring worker. The final run exited 0 and printed:

```text
PROBE_RESULT returned_normally=true failed_workers=1 submitted=450 feature_rows=23
```

The log also contains the deliberate IllegalStateException. This establishes that generateFeatureFile returns normally after a worker failure. It does **not** demonstrate that the entire raw pipeline would publish a valid cache in this exact fixture: an earlier optional sidecar step encountered an unrelated duplicate feature ID in the original shuffled fixture, so the final probe isolates the search boundary. The partial-cache risk follows from the caller publishing metadata after a normal return and has not been separately reproduced here.

This discarded-Future pattern already exists at `138e34f`; it is an inherited defect in the active CTX-016 path, not a regression attributed to r8. The correction should remain Context-side: retain/inspect Futures (or collect failures explicitly), propagate the original cause, preserve consumer cleanup, and prevent completed metadata publication on scoring failure. A regression should inject one failed task among successful tasks and require an overall failure plus recoverable incomplete artifacts.

### 2. P2 — preparation copies the entire peptide exclusion set for every precursor

Location: `src/main/java/org/searlelab/context/encyclopedia/ContextWorkingLibraryPreparer.java`, lines 160–175, particularly 168–169.

For each supported precursor, preparation copies all normalized target peptide sequences into a new HashSet and then copies all previously used same-charge decoys into it. With P supported precursors and U unique normalized target sequences, the target-set work alone is O(P×U), plus repeated growing decoy-set copies. Store hits do not bypass this work: store lookup occurs afterward. Sharing a completed working library avoids repeated preparations, but a new or changed large source library still pays the cost.

At P and U near 100,000 this implies roughly ten billion target-key insertions before counting the repeated decoy inserts. That is an algorithmic operation estimate, not a measured wall-clock profile or a claim that it explains all observed runtime. The supplied historical source library is recorded as having 99,147 distinct precursor entries; U need not equal P.

A small Context-only correction can initialize an exclusion set per charge once from target peptides, then add each successfully selected decoy to that charge's set in the same order. Before adopting it, confirm the upstream generator treats the supplied set as read-only and verify assignments byte-for-byte, including normalization/collisions, failed predictions and target-only cases. No predictor/dependency change is necessary. This review has not implemented the correction.
